# Agent 上下文与工具请求拼装契约

用户于 2026-10-08 确认：prompt 拼装应提前考虑 `soul.md`、人格、长期记忆、MCP tools 和 skill；当前实现范围只包含最基础的 tools。本文记录规划，不表示这些能力已经实现，也不将本次文档请求作为开始 G3 代码实施的授权。

关联：[第一阶段 G3](phase-01-tui-agent.md)、[模型运行时决策](decisions/0003-model-runtime.md)。

## 1. 统一拼装入口

在 `internal/agent` 内建立小型 PromptBuilder，统一产出项目自有 `model.ChatRequest`。它负责消息组织、工具声明、上下文预算和拼装摘要；工具实现、TUI、渠道和模型适配器不各自拼接 prompt。

“拼装”包含两个独立部分：

- `messages`：基础规则、被选中的上下文、会话历史、当前用户输入，以及本次 run 的工具调用轨迹。
- `tools`：工具注册表生成的名称、用途与参数 schema，作为结构化字段传入模型接口。

模型适配器将自有请求转换为供应商协议，包括工具声明、工具结果和必要的思考回传。PromptBuilder 不依赖 SDK 类型，不生成供应商专有 JSON。权限、allowlist、超时、次数和取消由执行代码约束，提示词只提供使用指导。

## 2. 来源与后续扩展规划

| 来源 | 内容及装配方式 | 当前范围 |
| --- | --- | --- |
| 基础规则 | Agent 的职责、回答原则、工具使用与失败处理原则；有独立版本 | G3 实现 |
| `soul.md` / 人格 | 同一个人格来源：身份、语气、偏好与长期行为风格；不再重复建立另一套人格 prompt | 后续接入，本期不读取或创建文件 |
| 运行环境 | 按需提供工作目录、会话环境等真实信息；与基础规则分开组织 | 预留，本期无需求不注入 |
| 长期记忆 | 按当前任务召回相关偏好或事实，标明来源；不把全部记忆塞进请求 | 随 G4a 独立审核 |
| skill | 按用户选择或已授权的任务匹配加载操作指导，保留名称与版本；不全量加载所有技能正文 | 随 G5 独立审核 |
| 本地 tools | 注册表提供结构化声明与执行入口，模型按协议请求，结果按 call ID 回填 | G3 只做计算器和时间工具 |
| MCP tools | 后续经适配器加入同一工具注册表，使用同一调用循环；外部工具名称需命名空间和冲突检测 | 后续独立接入，本期不连接 MCP 服务 |
| 会话与当前任务 | 已提交历史、当前用户输入与本次 run 的工具轨迹，保留角色和时间顺序 | G3 延续并扩展已有行为 |

`soul.md` 只承载人格；长期记忆负责事实和偏好的积累，skill 负责任务操作方法，tools 负责实际执行。将来使用 MCP 的资源或 prompt 时，它们也需要明确的上下文来源，不能因来自 MCP 就自动成为系统规则。

后续接入文件来源时，路径、启用状态和默认选择应在实际用户配置中可见；默认文件应可查看和修改。具体配置字段与默认资产生成随对应单元审核，本期不增加无消费者的配置字段或空加载器。

## 3. 组织顺序与来源边界

当前 G3 请求按以下顺序组织：基础规则消息 → 已提交的会话历史 → 当前用户消息 → 本次 run 已完成的 assistant 工具调用与对应 tool 结果。`tools` 与这些消息并列，而非重复嵌入用户输入。普通无工具对话也经过同一个入口。

未来扩展仍沿用这一结构：人格与基础规则分别标识；选中的 skill、运行环境和召回记忆作为带来源的上下文区块加入；不把所有文件连成一个无法区分来源的大字符串。基础执行约束优先，人格影响表达；skill 指导当前任务但不覆盖用户要求；记忆及工具结果作为参考数据，不授予新的执行权限。

来源标记帮助模型理解内容，不能保证模型永远遵循优先级。文件、记忆和外部工具结果中的指令不能绕过代码中的工具许可与参数校验，也不自动升级为基础系统规则。

每个 run 准备时确定基础规则、上下文来源和可用工具的快照；同一个工具循环中保持一致。下一轮模型请求复用这份快照并加入最新工具轨迹，不反复追加基础规则或重新加载文件。后续确需中途加载 skill/资源时，须显式记录新增来源并重新检查预算。

## 4. 当前 G3 的最小闭环

G3 只实现基础规则、结构化工具声明、会话消息和工具结果拼装，不提前实现人格加载、长期记忆检索、skill 选择或 MCP 客户端。

1. 工具注册表成为名称、说明、参数 schema、执行入口的统一来源；稳定排序，并检测重名。请求只声明获准且有执行入口的工具。
2. PromptBuilder 组织基础规则、历史和当前输入，并附上注册表声明。基础规则只说明何时使用工具、如何处理错误及如何根据结果回答，不复制完整参数 schema。
3. 流结束并确认工具调用字段完整后，校验调用 ID、名称和参数，再由 Agent 串行执行；不依据自然语言中的“我要调用工具”触发执行。
4. 保留模型返回的 assistant 工具调用消息，每个结果使用 `tool` 角色和对应 call ID 回填；失败也用结构化结果。需要回传的供应商思考字段按适配器契约保留，不因 UI 折叠而丢弃。
5. 再调用模型，直到得到最终回答或触及预算/取消/协议错误。工具循环轨迹先保留在 run 内，成功后作为完整消息组提交；失败/取消按现有规则隔离，不留下无对应结果的半组成功历史。

内置计算器只接受明确运算和数值，时间工具使用可注入时钟。继续沿用 G3 既定的只读范围、调用次数与 deadline，不由人格或 skill 更改执行权限。

## 5. 预算、trace 与验收

对消息与工具结果设定可复现的长度限制，超限结果提供明确的截断标记和结构化摘要；不伪造完整结果。裁剪历史时以完整对话/工具消息组为单位，保留当前任务与本次未完成工具组；无法容纳必要组时明确终止。准确 token 估算尚未具备时只报告实际长度与已知 usage，不把字符数当成 token 硬预算。

预留各来源的独立预算和省略原因，后续可先减少不相关记忆或未选中 skill，再裁剪旧历史；本期不增加通用检索框架或上下文压缩模块。

trace 记录基础规则版本、拼装哈希、历史消息数量、工具名称/schema 版本、各部分长度及裁剪原因。默认不落盘 prompt 正文、人格、记忆、skill 正文、原始工具参数或结果；未来敏感来源不要单独写可猜测内容的裸哈希。

G3 拼装验收要求：

- scripted fake 和协议 fixture 覆盖“用户 → assistant 工具调用 → tool 结果 → assistant 回复”，Generate/Stream 的消息语义一致。
- 工具声明与执行注册表一致；相同输入与固定环境得到稳定顺序和拼装摘要。
- 多次模型调用只出现一份基础规则；工具调用 ID 与结果严格对应；未知工具、参数错误、截断、重复 ID 和预算不足符合 G3 失败策略。
- 历史裁剪不拆工具组；取消/失败不污染已提交历史；日志不包含上下文正文或凭据。
- 未启用的未来来源缺席时，基础聊天和工具闭环正常运行；验收不要求存在 `soul.md`、记忆库、MCP 或 skill。

后续每接入一种来源，都独立验证启用/缺失、来源优先级、预算与脱敏，再扩展这份契约。当前只在文档预留职责与接入位置，不提前创建 `memory`、`skills`、`mcp` 包或注册新的审核单元。
